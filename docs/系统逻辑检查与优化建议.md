# 系统逻辑检查与优化建议

检查日期：2026-11-24。

本文是该日期的历史检查记录，测试数量和“当前”描述均对应当时版本。2026-11-27 的实际操作请参阅 [操作说明](操作说明.md)。此后已更新投稿按论文去重展示、客户关联删除、终止写作展示、分页和备份下载命名；原测试数字不代表最新验收结果。

本轮检查覆盖账户与隔离、客户与作者关联、全包/半包论文、写作、投稿与改投、终止结算、实际收支、版面费与利润、跟进、附件与版本、备份恢复和部署包。对能够确定的缺陷直接修复；涉及费用归属、审计制度或数据模型的功能调整列为建议。

## 已修复的问题

| 问题 | 原来的触发方式与影响 | 修复后的行为 |
| --- | --- | --- |
| 慢请求重新打开已关闭的页面 | 点击详情或编辑后立即关闭、切换模块，较晚返回的请求仍打开旧记录；先后打开两个客户或论文时也可能显示旧记录 | 论文详情、论文编辑、稿酬登记、客户详情、投稿及删除确认共用请求有效性校验。关闭、切换界面或后来的请求会使先前请求失效 |
| 旧刷新覆盖新数据 | 两次刷新乱序返回，或刷新期间已保存费用，新记录可能被较早的列表结果覆盖 | 只接纳当前有效的刷新结果；保存、删除、终止结算及文件上传提交到本地列表时使旧刷新失效 |
| 旧账号响应干扰新登录 | 退出后仍在返回的列表可能写回旧数据；上一登录的 401 响应可能让新账号退出 | 列表结果和身份失效处理核对发起请求时的登录标识，过期响应不更新当前账号状态 |
| 保存/删除结果关闭后来的表单 | 提交后关闭，再打开另一篇论文；先前操作成功时会关闭新表单、改掉筛选或切换模块。论文保存还可能把新抽屉的关联论文改成旧论文 | 成功结果仍更新所属记录；仅操作发起时的界面仍有效时，才执行原定关闭或跳转。客户、论文、投稿、收支、版面费和终止结算均覆盖此规则 |
| 删除成功后刷新失败被当成删除失败 | 部分客户、收支删除先等刷新才更新界面，刷新失败时用户无法确认是否已完成 | 先反映成功删除，再刷新；刷新失败明确提示“删除成功，列表刷新失败”，并同步客户汇总 |
| 论文编辑绕过期刊重复校验 | 投稿编辑会检查同一期刊的未结束/已发表记录，但通过论文编辑修改当前期刊可以绕过 | 两个入口执行一致的期刊重复校验，包含大小写、空白、全半角归一化；失败时不保存任何部分修改 |
| 论文入口可以无日期推进投稿状态 | 直接新建/编辑论文为“审稿中”等状态，可以缺少实际投稿日期，与投稿管理要求不一致 | 新建和实际推进状态时同样要求投稿日期；已有历史缺失数据仍可保留，不在读取或旧数据迁移时猜测日期 |
| 新建已发表论文缺少发表日期与时长 | 新建已发表记录复用了旧数据迁移逻辑，导致结束/发表日期为空、投稿时长未计算 | 新记录按投稿规则补齐结束及发表日期、计算时长；旧数据迁移继续保留未知日期 |

主要实现位于 `web/app.js`、`web/business.js`、`web/files.js` 和 `src/BusinessService.java`。新增回归覆盖请求乱序、关闭与切换界面、跨入口约束和原子回滚。

## 已核对的业务规则

| 模块 | 检查重点 |
| --- | --- |
| 账户 | 账号唯一性、独立空间、切换与重启后隔离、原密码验证、改密后的会话失效范围、请求校验 |
| 客户与作者 | 同名客户通过编号区分；同篇多作者不会重复累计论文数和费用；客户重命名、论文转移、删除后重新汇总 |
| 全包/半包 | 半包不保留写作任务、稿酬或写作付款；旧论文按全包兼容；费用调整不能抹掉实际付款 |
| 写作 | 日期先后、实际交稿同步状态、逾期计算、定金尾款拆分、金额精度与确认、重试不重复记账 |
| 投稿与改投 | 编辑保留投稿编号，改投新增记录；当前与历史记录分开；同一期刊重复检查；稿件版本固定关联 |
| 终止服务 | 影响整篇论文；保留原投稿、写作和金额约定；停止常规跟进；原因与最终结算必须确认；补款、退款、追回与付款分别登记 |
| 收支和利润 | 整数分计算；费用约定与实际流水分开；约定剩余额度校验；退款不超过已收、退回不超过已付；现金流与利润分开；未知版面费不提前确认利润 |
| 跟进 | 计划、到期、今天及未来七天口径；完成或终止的服务不再提醒；设置跟进日期必须说明事项 |
| 附件与恢复 | 格式及容量限制、加密保存、历史版本和投稿关联、上传重试、跨账号访问、备份完整性、恢复失败回滚 |
| 数据库与部署 | 独立 MySQL 实例中的真实读写、迁移、回滚、级联清理、跨模式备份与重启；部署包校验、内容排除与 Java 17 兼容性 |

## 优先优化项状态与后续建议

### 已落实：版面费按每次投稿分别核算

每次投稿分别记录版面费约定、付款、退款与最终成本；改投会新增费用记录，旧期刊的实付款不会抵扣新期刊待付额。

例如原期刊已付 500 元且不退，新期刊需付 1000 元时，整篇论文总成本为 1500 元，已付 500 元，新期刊仍待付 1000 元；费用归属、利润和退款上限均按投稿核算。

### 已落实：收支保留操作记录，提供冲销与凭证

流水记录经手账号并保留原始记录；不再直接删除收支，账务更正需填写原因并追加冲销，可关联后续重记。真实退款仍单独登记；凭证加密保存、关联流水并随备份恢复。

### P1：集中处理终止后的待结算事项

现有论文及收支详情能查看待退款、待补款、待付稿酬和待追回。建议增加“待结算”列表，按上述类型筛选，展示客户、写作者、金额、约定处理日期和登记入口，避免服务终止后结算任务被遗漏。登记仍须确认实际收付，不能由改变状态自动生成流水。

### P2：备份健康与容量提示

已有加密备份、附件完整备份以及部署端备份脚本。建议在设置页显示最近成功备份时间、业务/附件占用、完整性校验结果，临近容量限制时提前提醒。恢复前增加摘要预览，明确目标账号、将替换的客户/论文/附件数量。

### 部分已实现：跟进结果与下次安排

现已支持独立跟进事项、处理结果、完结、重新打开和处理历史。尚可增加“完成并安排下次”快捷操作；总览集中呈现逾期交稿、久审、未结清与待确认版面费等可操作事项。

### P2：数据增长后的查询性能

当前列表与客户汇总主要依赖读取完整工作空间，再由浏览器筛选分页。建议在数据规模增长时引入服务端查询、分页及汇总接口，详情、历史与文件列表按需加载。应先用接近实际规模的数据测量响应时间，再确定索引与缓存方案。

## 仍需明确的业务口径

- 服务尾款和写作尾款由每单约定、录用、发表或交稿中的哪个节点提醒；目前系统按实际登记，不自动触发付款。
- 终止后的“投稿/写作时长”是否冻结到终止日。当前原状态和原日期保留，未结束记录的计算时长仍可能随日期增长；冻结服务耗时与继续观察期刊外部审稿时长是两种不同需求。
- 改投时旧期刊不退的版面费如何确认为成本，历史按整篇论文记录的费用如何归属。

这些项目尚未擅自改变现有金额或生成实际收支。

## 检查边界

自动化使用临时数据和独立测试实例，不读取真实客户数据或变更现有业务记录。本轮没有可用浏览器，未完成实际页面布局、键盘操作和真实操作路径的浏览器验收。测试通过表示覆盖的场景符合预期，不等同于所有业务组合都已穷尽；建议后续按真实订单样例补充验收用例。
